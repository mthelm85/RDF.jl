Inference & Validation

RDFS Inference

RDF.jl implements RDFS forward-chaining materialization — computing the full deductive closure of a graph under the RDFS entailment rules.

RDF.infer_rdfs — Function
infer_rdfs(g::Graph; rules=[:subClassOf, :subPropertyOf, :domain, :range]) -> Graph

Return a new graph that is the RDFS closure of g — the original triples plus all triples derivable by the applicable RDFS entailment rules (forward-chaining to fixed point). g is not modified.

Available rules: :subClassOf, :subPropertyOf, :domain, :range.

closed = infer_rdfs(g)
entails(g, Triple(ex.alice, rdf.type, ex.Animal))  # checks via RDFS closure
source
RDF.infer_rdfs! — Function
infer_rdfs!(g::Graph; rules=...) -> g

In-place version of infer_rdfs. Adds all RDFS-entailed triples directly to g and returns it.

source
RDF.entails — Function
entails(g::Graph, t::Triple; regime::Symbol=:rdfs) -> Bool

Return true if g entails t under the given entailment regime.

  • :simple — checks direct membership (t ∈ g)
  • :rdfs — checks membership in the RDFS closure of g
entails(g, Triple(ex.alice, rdf.type, ex.Animal))
entails(g, Triple(ex.alice, rdf.type, ex.Animal); regime=:simple)
source

Available rules

SymbolRDFS ruleDescription
:subClassOfrdfs9, rdfs10, rdfs11Transitive class hierarchy + type propagation
:subPropertyOfrdfs5, rdfs7Transitive property hierarchy + triple rewriting
:domainrdfs2?x a ?C when ?x ?p ?y and ?p rdfs:domain ?C
:rangerdfs3?y a ?C when ?x ?p ?y and ?p rdfs:range ?C

All rules are applied by default. Pass a subset via the rules keyword to restrict which rules fire:

# Only subclass inference
closed = infer_rdfs(g; rules=[:subClassOf])

# All RDFS rules (default)
closed = infer_rdfs(g)

Example

using RDF

ex   = Namespace("http://example.org/")
rdfs = RDF.rdfs

g = Graph()
push!(g, Triple(ex.Cat,   rdfs.subClassOf, ex.Animal))
push!(g, Triple(ex.Tiger, rdfs.subClassOf, ex.Cat))
push!(g, Triple(ex.tigger, rdf.type,       ex.Tiger))

closed = infer_rdfs(g)

# Now derivable:
entails(closed, Triple(ex.tigger, rdf.type, ex.Cat))     # true via rdfs9
entails(closed, Triple(ex.tigger, rdf.type, ex.Animal))  # true via rdfs11+rdfs9

In-place materialization

infer_rdfs! modifies the graph directly (no copy):

infer_rdfs!(g)  # adds all RDFS-entailed triples to g

Entailment check

entails checks whether a graph entails a specific triple, optionally under a named entailment regime:

entails(g, Triple(ex.alice, rdf.type, ex.Animal))          # :rdfs (default)
entails(g, Triple(ex.alice, rdf.type, ex.Animal); regime=:simple)  # direct membership only

Validation

RDF.validate — Function
validate(g::Graph) -> Vector{ValidationWarning}
validate(ds::Dataset) -> Vector{ValidationWarning}

Check all literals in g (or ds) for conformance issues and return a list of ValidationWarnings. An empty list means no issues were found.

Checks performed:

  • Language tags must conform to BCP47 syntax
  • Lexical forms must be valid for known XSD datatypes
warns = validate(g)
isempty(warns) || foreach(w -> @warn(w.message), warns)
source
RDF.ValidationWarning — Type
ValidationWarning

A warning produced by validate, containing:

  • triple::Triple — the offending triple
  • message::String — human-readable description
  • code::Symbol — machine-readable code (:invalid_lang_tag, :ill_typed_literal)
source

validate checks every literal in a graph against its declared datatype. It returns a vector of ValidationWarning values describing any mismatches.

warnings = validate(g)
for w in warnings
    println(w.message, " at ", w.triple)
end

Checked datatypes

The validator checks lexical forms for the following XSD datatypes:

  • Numeric: xsd:integer, xsd:long, xsd:int, xsd:short, xsd:byte, xsd:nonNegativeInteger, xsd:positiveInteger, xsd:nonPositiveInteger, xsd:negativeInteger, xsd:unsignedLong, xsd:unsignedInt, xsd:unsignedShort, xsd:unsignedByte, xsd:decimal, xsd:float, xsd:double
  • Boolean: xsd:boolean
  • Date/time: xsd:date, xsd:dateTime, xsd:dateTimeStamp
  • Language tags: rdf:langString, rdf:dirLangString (RDF 1.2)

A ValidationWarning is produced (not an exception) to allow partial processing of real-world data that may have conformance issues.
